# Benchmark task set (draft v0.1)

200 tasks = 50 request slots x 4 boards, as in the Project 02 description
("about 200 tasks: around 50 requests and shapes x 4 common boards").

| File | What it is |
| --- | --- |
| `tasks.json` | The 200 tasks. Regenerated by the script, do not edit by hand. |
| `pi4_assembly_tasks.json` | Three supplemental Pi 4 screwed-lid requests with automatic STEP-based cutouts. |
| `generate_tasks.py` | Deterministic generator (fixed seeds, no network, standard library only). |

## Design basis (what comes from where)

From the course catalog (Project 02): the size (about 200 tasks, around 50 requests and
shapes x 4 common boards), the example request (ports on front/back, wall-mount holes), and
the list of checks (fit, ports, screws, lid, printability, adherence to the request).

Chosen by the benchmark author, not stated in the catalog: which 4 boards, the 8 task
categories, and the 4 clarification tasks per board. The variation factors (ports and sides,
lid style, wall-mount hole count, wall thickness) and the sentence patterns follow the fields
and supported patterns of the Agent's design spec v0.1 (PR #1), so the tasks can be sent to the
current mock Agent unchanged.

Consequences to keep in mind:
- Because the sentences follow the mock's own supported patterns, a high score here shows the
  mock handles its documented patterns. It is not evidence about free-form language understanding.
- `expected` only covers "adherence to the request". Fit, ports, screws, lid and printability are
  judged by the Geometry checks and the printed tests, not by these tasks.
- Not covered yet: user-supplied shapes (the catalog's "requests and shapes"), and
  wall thickness below the Geometry minimum (1.2 mm), so no task here is meant to fail printability.
- Some Pi 4 requests may be physically impossible on a rectangular case (see open question below).

## Boards

| `board_id` | Task prefix | Ports used in requests |
| --- | --- | --- |
| `raspberry_pi_4` | `BM-PI4-` | USB, Ethernet, HDMI, power |
| `raspberry_pi_3b_plus` | `BM-PI3-` | USB, Ethernet, HDMI, power |
| `raspberry_pi_zero_2_w` | `BM-PZ2-` | USB, mini HDMI, power, SD card |
| `arduino_uno_r3` | `BM-UNO-` | USB, power |

Raspberry Pi 4: board outline, mounting holes and connector heights/positions in
`geometry/board_data.py` were checked against the official mechanical drawing
(found by Shanning Xu). The port lists for Pi 3B+, Pi Zero 2 W and Arduino Uno are
from general knowledge and **must be checked against the manufacturers' drawings**
before the benchmark is frozen.

Open question for Geometry: on the Pi 4 the USB and Ethernet ports are on the short
edge, while power and micro-HDMI are on the long edge, so requests that put them on the
same wall (or on opposite walls) may not be physically possible. Confirm the board
orientation with Geometry before labelling such tasks.
Today only `raspberry_pi_4` exists in Geometry's `board_data.py`; the other
three boards need dimensions added before they can be run end to end.

## Task format

```json
{
  "task_id": "BM-PI4-025",
  "board_id": "raspberry_pi_4",
  "category": "multi_port_diff_sides",
  "difficulty": "medium",
  "request":  { "task_id": "...", "request_text": "...", "language": "en" },
  "expected": { "board_id": "...", "lid": "removable",
                "ports": [{"port": "usb", "side": "left"}],
                "wall_mount_holes": 0, "wall_thickness_mm": null,
                "needs_clarification": false }
}
```

`request` is exactly the Agent's `request.schema.json` v0.1 object (all 200
validate against it). `expected` describes what the user asked for. It does
not claim anything about physical fit; that is what the checks and the prints
measure.

## Slots per board (x4 = total)

| Category | Per board | Total | Purpose |
| --- | --- | --- | --- |
| basic (lid only, optional mount holes) | 6 | 24 | Sanity baseline |
| single_port | 8 | 32 | One opening, one side |
| multi_port_same_side | 8 | 32 | Several openings on one wall |
| multi_port_diff_sides | 8 | 32 | Openings on two walls |
| lid_variant | 6 | 24 | removable / snap-fit / screwed / no lid |
| wall_mount | 6 | 24 | 1-4 mounting holes plus ports |
| wall_thickness | 4 | 16 | 1.5 / 2 / 2.5 / 3 mm |
| clarify_* | 4 | 16 | Conflicting lid, non-existent port, vague request, inch unit. The right behaviour is to ask, not to guess. |

Difficulty: 96 easy, 88 medium, 16 hard.

## Known limits (be upfront about these)

- All requests are English and follow the sentence pattern the current mock
  Agent understands; this tests the pipeline, not free-form language
  understanding. Add a second, freer phrasing set if time allows.
- Only rectangular cases; irregular user shapes are a separate set (see
  `../protocol/shape_register.csv`).
- Slots 47-50 of each board are Agent-behaviour tests, not geometry tests;
  report them separately from the success rate.
- The 16 Pi 4 same-side and different-sides tasks carry the
  `unsupported_user_selected_opening_sides` geometry scope tag. They remain in
  the original extraction benchmark with their existing prompts and expectations.
- The supplemental assembly cohort runs through `POST /design` against the
  assembly-enabled Backend. It covers screwed lids with default or explicit
  2 mm walls and STEP-derived cutouts. Keep its results separate from the
  original 50 Pi 4 requests. Physical fit and printability are separate checks.

## Run

```
python benchmark/generate_tasks.py --out benchmark/tasks.json --assembly-out benchmark/pi4_assembly_tasks.json
python stats/run_backend_experiment.py --tasks benchmark/pi4_assembly_tasks.json --out stats/backend_qwen_pi4_assembly_results.csv
```

Start the assembly-enabled Backend with Qwen and the Pi 4 reference STEP before
running the second command. Use `--base-url` if it listens on a different port.
The CSV records spec match, generation status, and the assembly checks for validation
and application of the automatic cutouts.
